# Staging only your hunks

Everything here is about one situation: a file carries your change *and* someone
else's uncommitted change, and you must commit only yours without losing theirs.

Pick the cheapest recipe that fits; the order below is the order to try them.

## 0. Decide the mode first

| The ask | Mode |
| --- | --- |
| "commit these files", "commit it all as one separate commit" | whole file |
| "commit only my changes" | cut inside the file |

Whole-file mode is the maintainer's own preference when he says it (one foreign
line riding along is then acceptable, but name it in the handoff). Do not
silently choose cutting when the ask was whole-file, and never fold foreign work
into your commit without saying so.

Check first whether the split is still needed at all: if the other writer has
already committed their side, your shared file is no longer shared —
`git diff <file>` will show only your hunks and plain `git add <file>` is safe.
This happens often; re-read the diff instead of reaching for surgery out of
habit.

## 1. Patch straight into the index (no working-tree changes)

The safest recipe: your change is written as a patch and applied to the index
only. Nothing in the working tree moves, so there is nothing to lose.

```bash
git diff -- <file> > <tmp>/my.patch     # or hand-write the patch
# keep only your hunks; inside a mixed hunk drop their "+" lines
git apply --cached --check <tmp>/my.patch
git apply --cached <tmp>/my.patch
git add <the files that are entirely yours>
```

Traps:

- **Context lines are mandatory.** A hunk that starts immediately with a `-`
  line is rejected with "patch does not apply"; only `--unidiff-zero` can apply
  it, so write context instead. Two context lines are enough.
- `@@ -N,M +N,K @@` must be counted **against the index**
  (`git show :<path>`), not against the working file. `--recount` removes the
  arithmetic entirely — prefer it.
- Every line of a new insertion must start with `+`. Marking part of a new block
  as context yields the same "does not apply", and the only cure is rewriting
  the patch.
- **Never classify a hunk by its `@@` line.** That line carries the context of
  the enclosing selector (a CSS selector, a function signature), not the changed
  lines, so a "my hunk" test against it silently mismatches. Classify by the
  changed `+`/`-` lines — a fingerprint grep of your own identifiers works.
- A mixed hunk (their lines *inside* your hunk) is exactly where diff slicing
  fails and this recipe wins: the patch carries only your added line, while the
  rest of their edit stays in the file.

## 2. Reverse their hunks out, stage, put them back

Use when the split is inside a file you are already editing normally.

```bash
cp <file> <tmp>/<file>.bak
git diff -- <file> > <tmp>/theirs.patch   # keep only THEIR hunks
git apply -R --check <tmp>/theirs.patch
git apply -R <tmp>/theirs.patch           # working copy = HEAD + your change
git add <explicit paths>
cp <tmp>/<file>.bak <file>                # their WIP returns byte-for-byte
```

For a mixed hunk that cannot be reversed whole, delete their line by its unique
prefix after checking that the match is unique.

Byte comparison is the proof — `cmp <tmp>/<file>.bak <file>` must be silent. Do
not judge by re-reading the diff: once the index blob changes, the hunk
boundaries move and it looks as though their work moved too.

## 3. Blob surgery (generated files)

A lockfile or a manifest regenerated by a package manager cannot be
hand-split: the resolver rewrites unrelated blocks. Rebuild the file from `HEAD`
plus only your insertions, and leave the working copy (their entries and all) in
place as an unstaged modification:

```bash
git show HEAD:<file> > <tmp>/base
# add only your hunks to <tmp>/base
git hash-object -w <tmp>/base
git update-index --cacheinfo 100644,<sha>,<path>
```

Validate a crafted lockfile against the **committed** manifests in a throwaway
checkout — `git worktree add --detach <tmp> HEAD` then a frozen
`pnpm install --lockfile-only` — not against the current manifests, which
include their uncommitted work.

## 4. Split one file across commits without touching the working tree

Useful when a background build or test run is using the tree right now:

1. `git show HEAD:<file>` → intermediate content → `git hash-object -w`;
2. `git update-index --cacheinfo 100644,<sha>,<path>` → commit;
3. let the final content arrive later through a normal `git add`.

## 5. Verification, in the order that matters

```bash
git diff --cached --stat                      # exactly your files, exactly your counts
git diff --cached | grep -E "<their fingerprints>"   # must be empty
git status --short                            # MM: staged = yours, unstaged = theirs intact
```

- `MM` is the expected, healthy shape for a shared file: the first column is
  what you are committing, the second is their surviving WIP.
- Assert the file count inside the commit chain so an unexpected composition
  stops it (`[ "$(git diff --cached --name-only | wc -l)" -eq N ]`).
- For a long series, audit afterwards:
  `for c in …; do git show --stat --format="" $c | tail -1; done` against the
  file lists you intended.
- State plainly in the handoff that the gates ran in a dirty tree and describe
  the snapshot as `HEAD` + your additive change.

## 6. Undoing a broken series

`git reset --mixed <commit>` returns the changes to the working tree without
losing them, but the target must sit **before** the first broken commit —
otherwise the parent commit keeps the debris in history. If a foreign commit
must also be unwound, done in order: `git reset --soft HEAD~1`, then
`git restore --staged <their paths>`, then commit yours, then
`git add -A <their directories>` to hand their set back to the index.

## 7. Environment traps on Windows

- Git-Bash `/tmp` and native Node's `/tmp` are different directories: a path
  written by the shell must be converted (`cygpath -m`) before Node reads or
  writes it. Prefer the platform temp directory from the runtime
  (`os.tmpdir()`) over the literal `/tmp`.
- Text rewritten through `split("\n")` + `join("\n")` preserves `\r`, so a
  round-trip does not normalize CRLF — good for their WIP, bad if you expected
  normalization.
