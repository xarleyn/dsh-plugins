# Память домен-экспертов на SQLite (2026-09-23)

Предложение перевести хранение памяти домен-экспертов (`domain_experts.memory`)
с JSON-документа на SQLite. Повод — замеры боевого стенда 23.09 и рост, который
уже виден: тот же файл прошёл 56 390 → 103 237 байт за сутки, а носитель
перезаписывает документ целиком на каждую запись.

Жёсткое требование, из которого следует всё остальное: **уже накопленную память
не теряем ни на одном шаге**. Перенос — это импорт с проверкой и откатом, а не
пересев.

> **Статус (2026-09-24):** этап 0 и вариант B (этап 2) сделаны в плагине, ветка
> `feat/domain-experts-memory-sqlite`. Вариант A не начался по причине из
> раздела 3.1: включение `storage-sqlite` требует изменения харнесса (зависимость
> базового бандла + пересборка образа), а исходники харнесса этому репозиторию не
> принадлежат. Spec-решение о порядке из раздела 3 («если A упрётся в харнесс, B
> становится первым шагом») применено. Обвязка кита (этап 3) не начата.
>
> Принятые владельцем плагина решения (см. раздел 8): импорт живёт в провайдере
> плагина; ретенция/TTL в этом шаге не добавляем; `retrieve` — строгий паритет
> с нынешним ранжированием, FTS5 не используем.

---

## 1. Почему (замеры)

Боевой стенд, `data/dsh/storages/domain_experts.json` на 23.09:

| Что | Значение |
| --- | --- |
| Размер файла | 103 237 байт |
| `domains` | 8 записей, 50 136 байт сериализованно |
| `memory` | 30 записей, 40 115 байт сериализованно |
| Текст памяти | 31 046 символов, в среднем 1 035, максимум 1 632 |
| Пространства имён | `domain/answer-reviewer` 27, `domain/payments` 2, `domain/platform` 1 |

Имена пространств имён в таблице заменены на синтетические (`answer-reviewer` и
`platform` — общие, они же в примерах плагина): репозиторий публичный, и ключи
боевых доменов в его истории оставаться не могут. Числа — измеренные.
| Рост (git-история того же файла) | 56 390 → 103 237 байт за сутки |

Почему это больно уже сейчас, а не «когда-нибудь»:

- **Запись перезаписывает весь документ.** Носитель —
  `@deepseek-ai/dsh-storage-json`, снимок юнита целиком в памяти процесса;
  каждое `remember` сериализует и записывает файл целиком (temp + fsync +
  `rename` + fsync каталога). Стоимость записи растёт со всем, что когда-либо
  было записано.
- **Массовые операции умножают это на N.** `clear(namespace)` идёт по записям и
  делает по одному `delete` на каждую — то есть N последовательных перезаписей
  всего документа.
- **Чтение не индексировано.** `retrieve` (подбор памяти перед шагом эксперта)
  токенизирует и оценивает каждую запись таблицы в памяти; `listNamespaces` и
  `inspect` тоже обходят всё. Индексов, пагинации и точного фильтра по тегам нет.
- **Потолка роста нет.** `MAX_TEXT_LENGTH = 8 000` обрезает одну запись и только
  её; нет TTL, лимита на namespace, эвикции, компакции.
- **Открытие читает всё.** `loadAll` поднимает в память каждую запись юнита — при
  росте таблицы это и стартовая задержка, и постоянно занятая память.

Что наращивает объём: 19 учётных записей на стенде, каждая сессия-разбор пишет
несколько записей (например, `domain/answer-reviewer` — по записи на версию
разбора), теги копятся свободным словарём.

## 2. Где шов

`domain_experts.json` не пишет ни одна строка кода плагина. Плагин **объявляет
домен**, а носитель выбирается ниже — это и есть готовый шов для переезда.

| Слой | Кто | Что задаёт |
| --- | --- | --- |
| Плагин | `plugins/dsh-domain-experts/src/host/storage.ts` | `defineDomain({name: "domain_experts", version: 1, tables: {domains, memory}})` — только схема и версия |
| Форма домена | `@deepseek-ai/dsh-storage-domain` (`src/index.ts`) | `Config { backend, routes? }`: `backend` — маршрут по умолчанию, `routes` — переопределение **по домену**; неизвестный бэкенд падает на `open` с `backend-not-found` |
| Бэкенд-json | `@deepseek-ai/dsh-storage-json` | `config.root = dshHomePath('storages')` — откуда и берётся `storages/domain_experts.json` |
| Бэкенд-sqlite | `@deepseek-ai/dsh-storage-sqlite` | `config { path, journalMode? }`, один файл на все маршрутизированные юниты |

Ключевое следствие: переключение носителя для домена — **правка конфигурации
развёртывания, а не код плагина**. Плагин про смену носителя не знает (и по
спеке `SPEC.md` не должен: «One storage unit, `domain_experts`, with two tables»).

Ещё одна деталь, которая позже пригодится: интерфейс провайдера памяти
(`src/host/memory/registry.ts`) — **асинхронный** (`retrieve/inspect/remember/
forget/clear` возвращают Promise), а синхронный `MemoryTable` (`get`/`entries`)
— это только поверхность встроенного провайдера над снимком домена. Значит
провайдер со своей базой можно добавить, не меняя публичный контракт плагина.

## 3. Два варианта

### Вариант A — маршрут домена на `storage-sqlite` харнесса

```yaml
# профиль развёртывания (patch); строка-оверрайд переписывает config целиком,
# поэтому backend повторяется
- id: storage-domain
  config:
    backend: json
    routes:
      domain_experts: sqlite
- id: storage-sqlite
  name: '@deepseek-ai/dsh-storage-sqlite'
  config:
    path: /data/storages/domain_experts.db
```

Что известно про носитель (проверено 23.09):

- Версия `0.1.5-rc.2`, DDL: `units(name, version)`, `unit_globals(unit, value)`,
  `u_domain_experts_domains` и `u_domain_experts_memory` — обе
  `(key TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT`, значение = JSON записи;
  запись — `INSERT … ON CONFLICT(key) DO UPDATE SET value = excluded.value`.
- `journal_mode` по умолчанию `wal`; свой физический формат версионируется
  `PRAGMA user_version` и **не имеет миграций**: любая другая версия отвергается.
- Один файл на все маршрутизированные юниты.
- `loadAll` по-прежнему читает все строки при открытии — модель «снимок в
  памяти» не меняется.

**Готовность в образе стенда** (это и решает цену шага): пакет **собран в образе**
(`/app/packages/storage/storage-sqlite/lib/index.js`, `0.1.5-rc.2`) и линкован в
pnpm-сторе (`/app/node_modules/.pnpm/node_modules/@deepseek-ai/dsh-storage-sqlite`),
как и работающий сегодня `dsh-storage-json`. Но базовый бандл его в
`dependencies` **не объявляет** (`packages/bundle/base/package.json:86-88` —
только `storage`, `storage-domain`, `storage-json`), а на npm у обоих
`@deepseek-ai/dsh-storage-*` лежат только заглушки `0.0.1-rc.1`. То есть путь
включения — либо добавление зависимости в бандл (изменение харнесса + пересборка
образа), либо патч снапшота харнесса в ките развёртывания.

Что берёт: перезапись всего документа на каждую запись исчезает — запись
становится одной строкой. `clear(namespace)` — одним оператором вместо N полных
перезаписей.

Чего НЕ берёт: чтение остаётся полным сканом в памяти (`loadAll` + перебор в
провайдере), ретенции/TTL/индексов нет, файл становится бинарным (последствия
для git/синка — раздел 5).

### Вариант B — свой SQLite-провайдер памяти в плагине

Новый провайдер (`id: sqlite`) рядом с `builtin`, выбираемый в развёртывании
через `defaultMemoryProvider`, поверх `@yadsh/dsh-plugin-kit/sqlite`
(`packages/plugin-kit/src/sqlite.ts`: `node:sqlite` — `DatabaseSync`, WAL,
`synchronous = NORMAL`, `busy_timeout = 5000`, `chmod 0600`, миграции через
таблицу `qa_meta`, транзакции, отказ открывать базу новее своей схемы). Этим же
классом уже живут `qa-accounts.db`, `qa-quality.db`, `qa-capability-policies.*`,
`qa-integrations.db` — то есть прецедент в репозитории не теоретический.

Что берёт дополнительно к A: индекс по `(namespace, updated_at)`, FTS5 (или
эквивалент) под нынешнюю токенизированную выдачу `retrieve`, лимиты и
пагинацию, TTL/эвикцию, точечные выборки вместо полного скана.

Чем платим: память уходит из контракта storage-domain — правка `SPEC.md` (сейчас
там «один юнит, две таблицы»), своя валидация записей (zod `MemoryRecord`),
своя версионность/бэкапы. Плюс это код, который надо поддерживать, а не строка
конфигурации.

### Сравнение

| | A: маршрут домена | B: свой провайдер |
| --- | --- | --- |
| Изменение кода плагина | нет | да (провайдер + миграции) |
| Цена включения | зависимость бандла/патч + пересборка образа | релиз плагина (обычная волна) |
| Перезапись всего документа на запись | уходит | уходит |
| Полный скан на чтение | остаётся | уходит (индексы/FTS) |
| Ретенция/TTL/лимиты | нет | да |
| Обратимость | переключить маршрут обратно | импорт обратно в юнит |
| Контракт `SPEC.md` | не меняется | меняется |
| Риск | импорт и готовность бэкенда | объём кода и регресс выдачи `retrieve` |

**Рекомендация:** этап 1 — вариант A (дёшево, обратимо, снимает главную боль —
перезапись всего документа), этап 2 — вариант B, когда таблица пойдёт в тысячи
записей или понадобится ретенция. Если включение A упрётся в харнесс (см.
раздел 8), B становится первым шагом: он едет обычной волной плагинов и не
зависит от пересборки образа — урок 23.09 про отставший образ в силе.

## 4. Память не теряем

Обязательные требования к переносу — любому из вариантов:

1. **Импорт с подтверждением, а не пересев.** Порядок как в уже принятых в
   репозитории переездах (`plugins/dsh-qa-surface/src/admin/quality-store.ts`,
   `src/accounts/database.ts`, `plugins/dsh-qa-integrations/src/repository.ts`):
   импорт пропускается, если целевая база непуста; строки пишутся в одной
   транзакции; внутри неё же проверяется, что приехало всё; только после этого
   исходный файл переименовывается в `<имя>.migrated-<UTC-штамп>` — не удаляется.
2. **Проверка по записям, а не по счётчику.** Сравнить до/после: число записей,
   и поэлементно `namespace`, `key`, `text`, `tags`, `createdAt`, `updatedAt`
   (включая ту самую обрезку текста на 8 000 — она должна быть уже в исходных
   данных, а не появиться при импорте).
3. **Проверка выдачи.** Фиксированный набор запросов (5–10) прогнать до и после
   переезда и сравнить `retrieve` — порядок и состав. Переезд не должен менять
   ранжирование: сейчас это попадания токенов, затем `updatedAt`.
4. **Откат описан заранее.** JSON остаётся на диске; обратный маршрут
   (`routes.domain_experts: json`) возвращает прежний носитель; для B — обратный
   импорт из базы в юнит. Откат проверяется на стенде, а не предполагается.
5. **`QA_CONFIG_RESEED` не должен вытирать память.** Сейчас пересев — это
   «положить китовый сид поверх»; после переезда он обязан либо не трогать
   память, либо проходить через тот же импорт с проверкой.

Что сделано из этого списка и где отступление (24.09). Пункты 2, 3 и 5 закрыты
тестами и самой схемой: `memory-import.test.ts` сравнивает поля поэлементно и
проверяет откат, `memory-parity.test.ts` держит оба провайдера на одинаковой
выдаче, а памяти в юните после переезда нет — пересев сида её стереть не может
(см. 8.4). Пункт 4 для B = вернуть `defaultMemoryProvider: builtin`; на стенде
он ещё не проверялся, потому что кит базу не возит. Пункт 1 в части «исходный
файл переименовывается» сделан иначе и сознательно: плагин не знает, где лежит
документ юнита (носитель выбирается ниже него), поэтому оставляет копию
нетронутой, а архивированием файла занимается кит, которому путь известен.

## 5. Что это ломает в обвязке стенда (qa-deploy-docker)

- **git-карьве-аут.** `data/dsh/storages/domain_experts.json` специально
  трекается (см. комментарий в `.gitignore`), чтобы дрейф стенда и кита был виден
  диффом. Бинарную базу так не посмотреть: `scripts/qa-config-drift.sh` хеши
  сравнит, а `git diff` покажет «Binary files differ». Решение нужно принять
  явно: трекать `.db` (хешем, без диффов) или снять трекинг и полагаться на
  `qa-sync-*`.
- **Сидирование.** `docker/entrypoint.sh:398-413` (`install_storages`) копирует
  из кита только `*.json` — `.db`-сид будет молча проигнорирован. Либо учить его
  новому носителю, либо сеять через импорт.
- **Установка конфигов.** `scripts/qa-config-install.sh` держит в плане строку
  `config/dsh/storages/domain_experts.json` → рантайм-копия. 23.09 выяснилось,
  что этот шаг затирает накопленную память китовым сидом (30 записей против
  пустой таблицы) — сейчас он обходится вариантом скрипта без storages. При
  переезде шаг должен уметь новый носитель и сохранить запрет «память не
  уменьшается».
- **Синк.** SQLite едет тройкой `.db` + `-wal` + `-shm` и только при
  остановленном стеке — для `data` это уже правило (`QA_SYNC_PRE_SSH/POST_SSH`).
  Плюс вырастет вес `data`: сейчас файл 100 КБ, база с WAL будет больше.
- **Сид кита.** `config/dsh/storages/domain_experts.json` (56 КБ, память пустая)
  остаётся сидом для чистого стенда — просто его доставка в базу тоже требует
  импорта.

## 8. Открытые вопросы

1. **Где живёт импорт.** Решено (24.09): в провайдере плагина
   (`importFromUnit()`, вызывается при открытии хранилища). Вариант «в самом
   `storage-sqlite`» требовал бы харнесса, а вариант «разовый скрипт в ките» —
   держить знание о раскладке юнита вне плагина. Исходный документ при этом не
   переименовывается: плагин не владеет носителем юнита, и копия в юните — путь
   отката. Архивирование/переименование — шаг кита (этап 3), ему известен путь.
2. **Нужна ли `storage-sqlite` в базовом бандле.** Снято для этой задачи: память
   переехала вариантом B, который едет релизом плагина. Вопрос остаётся открытым
   для остальных юнитов и для этапа 1.
3. **Политика ретенции.** Решено (24.09): в этом шаге не добавляем. Ничего не
   удаляется молча; драйвер роста в долгую остаётся незакрытым, и отдельное
   решение по нему нужно принимать отдельно (TTL или лимит на namespace —
   удалённая память, а это уже не «носитель меняется»).
4. **`domains` оставляем в JSON?** Решено по факту: да. Память уходит в базу
   провайдера, таблица `domains` остаётся в юните — её правят сид и UI, и она
   маленькая. Побочный выигрыш: пересев сида (`QA_CONFIG_RESEED`) больше не может
   стереть накопленную память, потому что памяти в юните нет — требование 4.5
   закрывается этой схемой, а не особым кодом.
5. **Трекинг базы в git** (см. раздел 5). Не решено — вопрос этапа 3, он про
   кит, а не про плагин.

## 9. Не делаем

- Не меняем схему записи `MemoryRecord` (zod, все поля обязательные): формат
  записи остаётся прежним, поэтому версия юнита остаётся `1`.
- Не делаем провайдер синхронным и не меняем публичный контракт
  `DomainMemoryProvider` (он уже async).
- Не переводим остальные юниты (`workspace`, `session_projcache`,
  `message_feedback`) — только `domain_experts.memory`.
- Не добавляем sqlite обязательной зависимостью плагина: вариант A кода плагина
  не трогает вовсе.
