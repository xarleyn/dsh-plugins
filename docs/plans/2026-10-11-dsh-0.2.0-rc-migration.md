# План перехода плагинов на DSH 0.2.0-rc.2

Статус: **этап 1 (однородная dependency-база) выполнен 12.10; приемка на Host,
пакетные metadata этапа 3 и выпуск не выполнены**.
Дата исследования: 2026-10-11. Дата проверки этапа 1: 2026-10-12.
Рабочая линия: `dsh-v0.2.0-rc` в Gitea.

## 1. База и границы

Ветка плагинов создана от проверенного `main`
`63cd4f4fc7c397b19cd664682a2e7df4211d9091`. Старая линия
`dsh-v0.1.7-rc` заканчивается на `ae88c8b150980d224357bed2e8e9dd8d1a419079`;
деревья этих коммитов одинаковы. Новый branch сохраняет весь результат предыдущей
миграции и исправления зависимостей из main.

Целевой релиз относится к **Host**, у которого отдельная Git-история:

| База Host  | Git-тег           | Коммит                                     |
| ---------- | ----------------- | ------------------------------------------ |
| 0.1.7-rc.2 | `dsh-v0.1.7-rc.2` | `477b4f420553e8a52c2fbccc464d7561b239c443` |
| 0.2.0-rc.2 | `dsh-v0.2.0-rc.2` | `639ed015397290b3745d163aafe02ffee4aa3f84` |

`v0.2.0-rc.2` — название GitHub Release; фактический Git-тег имеет префикс `dsh-`.
Ветка плагинов начинается от собственного main, а эти теги задают контракт Host.

Исследование фиксирует Git-объекты обоих тегов, опубликованные npm-пакеты и
потребителей в плагинах. Пробные изменения зависимостей и воспроизводящий тест
не входят в рабочую линию. Этот документ не разрешает выпуск npm, слияние в main,
изменение действующего deployment или перезапуск общего стенда.

Метки доказательств:

- **Измерено**: установка, компилятор, тест или непосредственное сравнение объектов Git.
- **По исходникам**: контракт прочитан на фиксированном теге; отдельный deployment не запускался.
- **Нужно проверить**: приемка на реальном Host, браузере или данных пользователя.

## 2. Размер изменения и общий вывод

**Измерено:** между тегами Host 448 коммитов, 1638 изменённых файлов,
52060 добавленных и 82531 удалённая строка. Из них 252 изменённых файла находятся
под `packages/*/*/src/`; большой общий diff также включает документацию,
публикационные файлы и снимки.

Плагины объявляют 55 разных зависимостей `@deepseek-ai/*`: 52 пакета семейства Host
и три независимых framework-пакета. Все 55 имён сохранились; их export maps
между тегами не изменились. В 14 непосредственно используемых пакетах изменились
исходники. **Измерено на обоих тегах** (`vendor/` Host): Cordis 4.0.4,
plugin-loader 1.0.5 и schemastery 3.18.4 не изменились между 0.1.7-rc.2 и
0.2.0-rc.2, поэтому известная поломка «host 3.18.2 + плагины 3.18.4 =
codec not backed by zod v4» на этом переходе не воспроизводится. Эти три пакета
всё равно нельзя обновлять до номера версии Host — они живут своей линией.

В Host добавлены четыре пакета: `dsh-client-product-analytics`,
`dsh-client-ui-settings-session-log`, `dsh-experimental-schedule-bundle`, `dsh-otel`;
пакеты Host из сравниваемого списка не удалены.

**Измерено:** на однородном дереве зависимостей 0.2.0-rc.2 typecheck и build
прошли для всех 34 проектов с такими целями. Тесты шести приоритетных проектов
прошли: 2927 passed, один существующий opt-in тест пропущен. Это хороший признак
для переноса API, но не доказательство готовности приложения на реальном Host.
Основной риск находится в составе профиля, peers и новых runtime-сценариях.

## 3. Обязательный первый этап: однородные зависимости

Простая замена версий в `catalog:dsh-dev`, диапазонов в `catalog:dsh` и литералов
provider-extended **не достаточна**. Пробный lockfile сохранил 26 имён пакетов
Host 0.1.7-rc.2; pnpm сообщил конфликты peers. Повторное разрешение без корневого
lockfile тоже оставило старые версии. Одни записи каталога не задают версию
автоматически установленных peers, если их не использует dependency edge.

**Измеренное решение для пробы:** явные development roots для этих 26 имён
на 0.2.0-rc.2. После этого исчезли все снимки старых пакетов Host и сообщения
о конфликтующих peers.

**Выполнено на этапе 1 (12.10):** корни объявлены в корневом манифесте через
`catalog:dsh-dev` — в базе там жил только `cordis`, так что 26 записи добавлены,
а не переписаны. В каталоге `dsh-dev` не хватало 10 ключей из этого набора:
`dsh-atomic-write`, `dsh-client-file-upload`, `dsh-config-editor`,
`dsh-llm-retry`, `dsh-ptc-runtime`, `dsh-token-meter`, `dsh-typert-protocol`,
`dsh-util-crypto`, `dsh-util-time`, `dsh-util-values`,
`dsh-util-workspace-path`; они заведены. Две грабли вылезли из самих же правил:
как только `dsh-util-values` появился в каталоге, литеральный dev-pин в
`dsh-llm-provider-extended` стал нарушением §27.12 и переведён на
`catalog:dsh-dev`, а новый однородный граф потребовал `pnpm dedupe` (§27.5) —
без него `deps:check` краснеет, несмотря на отсутствующие peer-конфликты.
Восемь peer-литералов provider-extended остались литералами: `deps:check` сам
перечисляет их как намеренно более широкие публикуемые peer-диапазоны.
Пакеты Host остаются dev/peer-зависимостями: не переносить их в обычные
runtime `dependencies` плагинов.

### Диапазон совместимости имеет ловушку prerelease

Host проверяет DSH peers с `includePrerelease: true`. Измерено через semver:
`>=0.1.7-rc.2 <0.2.0` **принимает 0.2.0-rc.2 в Host**, хотя обычная проверка
semver его отвергает. Поэтому успешный preflight старого пакета не доказывает
тестирование 0.2, а верхняя граница `<0.2.0` не изолирует следующий minor RC.

Для первой реализации зафиксировать dev baseline ровно `0.2.0-rc.2`.

**Принято владельцем 12.10:** публикуемый поддерживаемый диапазон — вся линия
от 0.1.7 до 0.3.0, то есть `>=0.1.7-rc.2 <0.3.0-0`. Верхняя граница через `-0`,
чтобы `includePrerelease` Host не пропустил в неё RC следующей минорной линии;
отрицательные случаи (`0.1.7`, `0.3.0-rc.1`, `0.3.0`) проверены на тот же
экземпляр semver, что и Host.

Разделение обязано быть именно таким, потому что механика гейтов его не сторожит:
`run-verify-package.mjs` требует от `deepseekHarness.range` только непустоты
(строка 283), а `verify-package-hygiene.mjs` — непустоты и наличия хотя бы одной
записи в `testedReleases` (строки 350, 361). Из 28 `compatibility.json` ни один
диапазон не сверяется с манифестами, поэтому широкий `range` с пустым списком
проверенных релизов прошёл бы зелёным. Отсюда порядок: `range` переезжает вместе
с зависимостями на этапе 1, `testedReleases` пополняется `0.2.0-rc.2` только после
приемки этапа 2. Исключение из этого правила три — `dsh-jev-compaction`,
`dsh-llm-provider-extended` и `dsh-openviking-memory` пинят `testedReleases`
массивом прямо в своих `scripts/verify-package.mjs`, так что их правка обязана
лежать в том же изменении, что и `compatibility.json` этапа 3, иначе гейт
покраснеет на ровном месте. Один тест (`dsh-openviking-memory/tests/bundle.test.ts`)
пинил и сам диапазон; он обновлён на этапе 1 вслед за контрактом.

### QA timed questions: подтвержденный пробел

Текущий `QaQuestionRequest` структурно описывает старый waterfall и не несёт
`wait`; `QaPendingQuestion` не сохраняет Host callId. `QaQuestionGate.park`
удаляет pending form при abort, а idle также завершает ожидание. На rc.2 Host
после timed timeout допускает поздний ответ через durable projection и новый
пользовательский turn — этот путь QA пока не обслуживает.

Воспроизводящая проба использовала настоящий `TimedQuestionWait` из pinned Host
и настоящий QA gate: вопрос появился, по истечении unclaimed wait форма исчезла,
причина отобразилась как закрытие пользователем, поздний `gate.answer` вернул false.
Вторая проверка подтвердила запрет native `userQuestions/attachWait` и
`userQuestions/answer`. Эти два успешных теста **подтверждают пробел**;
они не подтверждают исправление или интеграцию реального Host service.

Timed — opt-in, default Host остаётся `legacy`. Поэтому это отдельная feature
задача, а не обязательное включение при смене версии. При её реализации нужны:

1. Стабильные `callId` и состояния open/continued/settled в QA API и UI.
2. Owner-only ответ с проверкой session, chat и account; запрет чужих, дублированных
   и устаревших ответов и защита от параллельного admission.
3. Business wait claim и disconnect/reconnect с Host remaining duration.
4. Поздний ответ через механизм Host, с сохранением источника сообщения и replay.
5. Подписка на `userQuestions` projection; завершённый agent turn не удаляет
   продолжающийся вопрос. Чужие и operator-only вопросы остаются вне QA.
6. Timeout не заменяет обязательное человеческое одобрение документа или операции.

## 5. Порядок реализации

### Этап 0 — фиксированная база: выполнен

Создать branch от main, сравнить pinned Host tags, проверить npm availability,
составить inventory и пробу, сохранить план. npm подтвердил 0.2.0-rc.2 для Host,
settings-account и schedule-bundle; используемые development roots установлены.
Исторические migration docs не переписывать как актуальный вердикт.

### Этап 1 — dependency baseline и обязательные адаптации: выполнен 12.10

В одном согласованном изменении обновить catalogs, literal provider peers,
developer roots и lockfile. Проверить отсутствие смешанных Host versions,
peer конфликтов и вторых framework instances. Сохранить dependency boundaries
и security overrides. Typecheck/build всего дерева; затем тесты всех проектов.
Разобрать runtime-изменения из матрицы, сохранив `legacy` вопросов.

Готовность этапа: dependency graph однороден, frozen install и audit проходят,
компиляция и тесты зелёные. Один exit 0 от pnpm при peer warnings не принимается.

Результат прогона на линии `dsh-v0.2.0-rc` (после вливания `main` `0f3d409c`,
шесть коммитов поверх базы плана, включая волну `release/2026-10-11-2`):

- `pnpm install --lockfile-only` и `pnpm install --frozen-lockfile` — без
  peer-конфликтов; в `pnpm-lock.yaml` ноль ключей Host `0.1.7-rc.2`.
- Второй экземпляр framework не появился: `cordis` резолвится только 4.0.4,
  `cordis-plugin-loader` только 1.0.5, `schemastery` только 3.18.4.
- `pnpm dedupe` понадобился как часть этапа (§27.5), после него компиляция
  и тесты прогнаны заново.
- `typecheck` и `build` — «Successfully ran targets ... for 34 projects».
- `test` — «Successfully ran target test for 35 projects», 7237 прошло,
  21 opt-in/skipped, ноль падений.
- `pnpm lint:workspace` и `nx run-many -t lint --skip-nx-cache` — 36 проектов,
  что и требует `agents.md` после пачки мержей; цифра 36 из DoD подтверждена.
- `pnpm deps:check`, `pnpm check:files`, `pnpm verify:seats`, `pnpm format`,
  `pnpm test:release`, `pnpm verify:packages` (32 publishable пакета) и

- Исходники плагинов этап 1 не менял: компиляция и тесты зелёные на прежнем
  коде, поэтому runtime-строки матрицы (Jev recovery, submission metadata,
  Work details, тема) остаются проверками этапа 2, а не правками этого этапа.

Побочная находка: `main` на `0f3d409c` сам не проходил `pnpm format` — коммит
`ea71ad63` оставил строку сверх print width в
`plugins/dsh-qa-surface/tests/client/components/qa-welcome-notice.test.tsx`.
На этой линии она исправлена отдельным коммитом (только перенос, смысл тот же),
но красный `pnpm check` улетел в main, и его нужно долить туда же.

### Этап 2.0 — перепин QA-deploy-кита (перед приемкой)

Приемка этапа 2 поднимается не «в вакууме», а из кита `dsh-qa-deploy-docker`,
где версия харнесса запинена, поэтому между этапом 1 и этапом 2 стоит свой шаг:

- перепин пина харнесса на `0.2.0-rc.2` и проверка, что ряд патчей кита
  ложится по своему порядку (на rc.2 это было девять патчей, где 0006 зависит
  от 0002); порядок применения — часть приема, а не деталь сборки;
- `pnpm install` внутри профиля с свежей волной требует флага, обходящего
  `minimumReleaseAge`, иначе установка профиля уходит в restart-loop;
- `/qa` должен открыться до начала сценариев: на прошлой перепинке 404 на этом
  маршруте был блокером, и проверка «образ поднялся» его не ловит;
- сборка кита затирает общий `latest`-тег, поэтому перепин делается на отдельном
  теге, а `data`-файлы профиля, которые пулл откатывает, возвращаются из HEAD.

Кит — отдельный репозиторий вне этой линии; шаг не разрешает изменение
действующего развертывания и не трогает занятый стенд.

### Этап 2 — установка и приемка на Host

В новом изолированном профиле установить **полный** `@deepseek-ai/dsh@0.2.0-rc.2`
и tarballs плагинов. Успешная установка части SDK не заменяет этот шаг.
Проверить обычный и QA account transport, owner/subscription/revocation границы,
новый чат, fork, restart/reload, live/history, конфигурационные карточки и
документный workflow. Jev/pruning проверять на копии данных, включая замену
tool/result после завершённого turn и последующую загрузку через reader.

Если профиль использует Schedule, согласовать его bundle и сохранить существующие
tasks/overrides. Реальные общие профили обновлять отдельной подготовленной операцией
после проверки изолированного профиля; занятой стенд не перезапускать.

### Этап 3 — доказанная совместимость и пакетные gates

После реальных проверок обновить `compatibility.json`, `testedReleases`,
README/NOTICE, generator templates и expectations в verify scripts.
Обновить `docs/COMPATIBILITY.md` и текущие verification инструкции; сохранить
исторические записи о предыдущей линии. Не маркировать 0.2 tested заранее.
Повторить package/consumer и tarball gates после metadata изменений.

Согласовать новые Nx version plans с уже существующими планами main. Для изменения
публичного Host peer baseline оценить minor bump у пакетов 0.x, не делать автоматический
patch всей линии. Реальное покрытие изменённых публикуемых проектов определяет
`release:check`. QA version plan сопровождается `QaChangelog.tsx` для планируемой
версии; опубликованные entries и package.json.version вручную не менять.

### Этап 4 — отдельные opt-in возможности

При необходимости реализовать QA timed questions по acceptance выше; добавить
новые пользовательские сценарии и их планы/заметки в той же задаче. Отдельно
решить, нужны ли Schedule и новые diagnostics профилю. Подключение product analytics
не входит в обязательную миграцию SDK.

### Этап 5 — CI, слияние и выпуск

Полный local gate и GitHub CI на точном SHA. Сохранить GitHub matrix/job shape;
проблемы Gitea runner исправляются на стороне mirror. Только после terminal green
и отдельного разрешения выполнять merge/release/deployment. Источник ветки находится
в Gitea; GitHub PR/ветка для релизного CI в этой задаче не создавались.

## 6. Команды и definition of done

Проба на 2026-10-11:

```bash
pnpm install --frozen-lockfile
pnpm nx run-many -t typecheck build --skip-nx-cache --output-style=static
pnpm nx run-many -t test --projects='@yadsh/dsh-qa-surface,@yadsh/dsh-jev-compaction,@yadsh/dsh-draft-sessions,@yadsh/dsh-session-audit,@yadsh/dsh-llm-provider-extended,@yadsh/dsh-sleev' --skip-nx-cache --output-style=static
pnpm audit --audit-level=high
```

Nx запускался с `NX_DAEMON=false`, `NX_PARALLEL=2`. На однородном trial graph:
install прошёл без peer conflicts, typecheck/build — 34 проекта,
test — 6 проектов, 2927 passed / 1 baseline opt-in skipped,
audit — No known vulnerabilities found. Полная перепись lockfile не нашла старых
Host 0.1.7-rc.2. Это результаты temporary trial, не состояние committed branch.

Финальные gates для реализации:

```bash
pnpm install --frozen-lockfile
pnpm check
pnpm lint:workspace
pnpm nx run-many -t lint --skip-nx-cache --output-style=static
pnpm verify:seats
pnpm verify:pr-rules --base=<pinned-main-sha> --head=HEAD
pnpm release:check --base=<pinned-main-sha> --head=HEAD
pnpm audit --audit-level=high
pnpm tarball:verify
git diff --check
```

Готовность миграции означает: однородный граф, корректные peers/metadata,
успешные 36 lint targets и остальные существующие workspace targets, чистая
установка полного Host и tarballs, реальные Web/QA/account/Desktop сценарии по
применимости, reload/replay без потери данных, подтверждённые планы версий и
terminal GitHub CI на том же SHA. Любая красная проверка получает конкретную
причину и исправление; опускать assertions, gates или source budgets нельзя.

Не измерено в этой задаче: полный Host boot, browser E2E на новом Host,
данные живого профиля, native Desktop и полный tarball gate для нового SDK.
Полная миграция не объявляется готовой на основании компиляционной пробы.
