# Shared DSH UI Kit Specification

Status: Implemented (2026-09-05) — landed as `@yadsh/dsh-plugin-kit/client` in `packages/plugin-kit/src/client/`; all four card clients migrated  
Date: 2026-08-31  
Package: implemented inside `packages/plugin-kit` (no separate ui-kit package)  
Workspace path: `packages/plugin-kit/src/client`

## 1. Summary

Create a publishable, browser-safe workspace package containing the shared UI
contract used by DSH plugin configuration cards. The initial package owns the
canonical card shell, its disclosure behavior, and lifecycle-safe style
installation. Plugin-specific forms, settings state, localization, and remote
calls remain in the consuming plugins.

The package is a library that is bundled into every consuming plugin's classic
browser bundle. It is not a DSH plugin, does not declare `dsh.client`, and does
not register itself with `window.__ModuleLoader__`.

## 2. Problem

`dsh-doc-impact`, `dsh-plugin-log-ui`, `dsh-prompt-firewall`, and `dsh-sleev`
currently carry independent copies of the same card markup, SVG chevron, and
canonical shell CSS. Static verification catches some drift after it happens,
but duplication still makes drift easy to introduce and requires coordinated
manual edits.

The shared contract needs one source of truth without weakening these runtime
requirements:

- every plugin still ships a self-contained `lib/client.js`;
- every client bundle registers its own full npm package name;
- no extra runtime ModuleLoader dependency is introduced;
- React remains supplied by the DSH web host;
- the canonical shell CSS remains physically present in each built plugin
  bundle so packed-package verification can inspect it.

## 3. Goals

1. Provide one typed implementation of the standard plugin card shell.
2. Provide one exact canonical CSS string matching the repository `AGENTS.md`.
3. Prevent plugin-specific classes and visual treatment from leaking into the
   shared header and outer shell.
4. Deduplicate style elements safely when several plugin bundles are mounted.
5. Preserve self-contained plugin bundles by bundling UI-kit code at build
   time.
6. Make the package usable by first-party and third-party DSH plugin authors.
7. Keep package and bundle verification able to detect identity, packaging,
   CSS, and externalization regressions.

## 4. Non-goals

- A general-purpose component library or design system.
- Wrappers for every input, button, table, badge, or form field.
- A settings data model, staging controller, or persistence API.
- Localization or remote-service abstractions.
- Runtime registration as an independent DSH client module.
- Replacing DSH design tokens or changing the current card appearance.
- Moving plugin-specific body CSS into the shared package.

## 5. Package identity and publication

The package must use the following identity:

```jsonc
{
  "name": "@yadsh/dsh-ui-kit",
  "version": "0.0.0",
  "type": "module",
  "sideEffects": false,
  "main": "./lib/index.js",
  "types": "./lib/index.d.ts",
  "exports": {
    ".": {
      "types": "./lib/index.d.ts",
      "default": "./lib/index.js"
    },
    "./package.json": "./package.json"
  },
  "files": [
    "lib",
    "README.md",
    "SPEC.md",
    "compatibility.json",
    "LICENSE"
  ]
}
```

Additional requirements:

- The package is public and uses the repository's canonical npm publishing,
  repository, homepage, bugs, license, and provenance metadata.
- It must be added to `nx.release.projects`.
- Its first release must use an Nx version plan.
- It has no `cordis.patch.yml` and no `dsh` manifest block because it is not a
  plugin.
- It imports nothing from `plugins/*` and has no Node-only dependency.
- `react` and `react-dom`, if needed by the final implementation, are peers;
  exact development versions and their type packages are dev dependencies.

## 6. Public API

The initial public surface must stay deliberately small:

```ts
import type { ReactNode } from "react";

export const PLUGIN_CARD_SHELL_CONTRACT_VERSION: 1;
export const PLUGIN_CARD_SHELL_CSS: string;

export interface PluginCardProps {
  readonly title: ReactNode;
  readonly description: ReactNode;
  readonly badge?: ReactNode;
  readonly showLabel: string;
  readonly hideLabel: string;
  readonly defaultOpen?: boolean;
  readonly children: ReactNode;
}

export function PluginCard(props: PluginCardProps): ReactNode;

export interface PluginCardStyleLease {
  dispose(): void;
}

export function installPluginCardStyles(
  target?: Document,
): PluginCardStyleLease;
```

No public type may contain `any`. Internal compatibility boundaries should use
`unknown` and narrow explicitly.

### 6.1 `PluginCard`

`PluginCard` owns only disclosure state and shell markup. It must render:

```text
li.dsh-plugin-card[.dsh-plugin-card--open]
└── button.dsh-plugin-card__header
    ├── span.dsh-plugin-card__head-text
    │   ├── span.dsh-plugin-card__name
    │   └── span.dsh-plugin-card__description
    ├── span.dsh-plugin-card__badge       (optional)
    └── svg.dsh-plugin-card__chevron
└── div.dsh-plugin-card__body             (open only)
```

Behavioral requirements:

- The header is `<button type="button">` and spans the full card width.
- `aria-expanded` reflects the current open state.
- The accessible label is `showLabel` while closed and `hideLabel` while open.
- The body is absent from the rendered tree while closed.
- The SVG is 14 by 14, uses `viewBox="0 0 14 14"`, and contains the path
  `m3.5 5.25 3.5 3.5 3.5-3.5` with `currentColor`, round caps, and round joins.
- Consumers cannot attach classes to the root, header, badge, or chevron.
- Consumers decide whether a card exists at all. If a settings namespace is
  unavailable, the consumer returns `null` before rendering `PluginCard`.

### 6.2 Canonical CSS

`PLUGIN_CARD_SHELL_CSS` contains exactly the canonical shell rules from the
repository `AGENTS.md`, in the same order and with the same declarations. It
must not contain plugin-specific selectors, resets, media queries, or body
control styles.

Changing this string is a UI contract change. Such a change requires:

1. an explicit review against the first-party DSH card;
2. updated package tests;
3. rebuilt consuming plugin bundles;
4. version plans for the UI kit and every published plugin whose bundled copy
   changes.

### 6.3 Style installation and disposal

`installPluginCardStyles()` is the only DOM side-effect API. Importing the
package itself must have no side effects.

The installer must:

- default to the ambient `document` but accept an explicit document for tests;
- create at most one style element per document;
- identify the style with a stable data attribute;
- share a reference count across separately bundled copies by storing state on
  `globalThis` under `Symbol.for("@yadsh/dsh-ui-kit/plugin-card-styles")`;
- return an idempotent lease;
- remove the style only when the final live lease is disposed;
- recover if the style element was removed externally while leases remain.

This makes independent plugin mount/unmount cycles safe without requiring a
separate runtime UI-kit module.

## 7. Build and dependency model

The UI kit itself builds ESM JavaScript and declarations from TypeScript/TSX.
It does not produce a classic ModuleLoader bundle.

Each consuming plugin declares:

```json
{
  "dependencies": {
    "@yadsh/dsh-ui-kit": "workspace:^"
  }
}
```

Every consuming client build must bundle `@yadsh/dsh-ui-kit` and must keep
these host-provided modules external:

- `react`
- `react/jsx-runtime`

The finished plugin bundle must not contain a runtime
`require("@yadsh/dsh-ui-kit")`. It must still contain the canonical CSS and the
plugin's own ModuleLoader registration:

```js
window.__ModuleLoader__.load({
  id: "<full consuming package.json.name>",
  factory: (require) => { /* bundled client */ },
});
```

The UI kit package must never be added to `dsh.client.inject`; it is a build and
npm dependency, not a host-provided client service.

## 9. Consumer migration

Consumers migrate one at a time in this order:

1. `dsh-sleev`
2. `dsh-plugin-log-ui`
3. `dsh-prompt-firewall`
4. `dsh-doc-impact`

For each consumer:

1. add `@yadsh/dsh-ui-kit` as a workspace dependency;
2. externalize only React and DSH host modules, not the UI kit;
3. replace the local canonical CSS, chevron, and outer card markup with the
   shared API;
4. keep plugin-specific classes inside the body;
5. install styles from `apply()`/effect setup and dispose the returned lease;
6. retain bundle verification for the full consuming package name, canonical
   CSS, SVG path, and absence of legacy shells;
7. assert that the built bundle does not require `@yadsh/dsh-ui-kit` at runtime;
8. run package and packed-tarball verification.

The generator's existing `--with-ui` path must be updated or confirmed to
produce this dependency, imports from the public package export, React
externals, and the required verification gates.

## 10. Verification requirements

### 10.1 UI-kit tests

- Closed card renders only the standard header and reports
  `aria-expanded=false`.
- Clicking the header opens the card, switches the accessible label, rotates
  through the open class, and renders the body.
- Optional badge ordering is title/description, badge, chevron.
- Chevron attributes and path match the contract exactly.
- Canonical CSS equals the `AGENTS.md` contract byte-for-byte after normalized
  line endings.
- Two installers in one document create one style; disposing one keeps it;
  disposing both removes it.
- Repeated disposal is harmless.
- Importing the package without calling the installer does not touch the DOM.

### 10.2 Package gates

- `lib/index.js` and `lib/index.d.ts` exist.
- Every `exports` target exists in the packed tarball.
- Packed metadata contains no `workspace:` or `catalog:` protocol.
- The tarball installs and imports in a clean environment with compatible React
  peers.
- The package contains no `dsh.client`, Cordis patch, ModuleLoader registration,
  plugin import, or Node builtin import.

### 10.3 Consumer gates

For every migrated plugin, the built and packed client bundle must assert:

- ModuleLoader `id` equals the full consuming package name;
- canonical shell rules and SVG path are present;
- both font chevrons `⌄` and `▾` are absent;
- legacy outer-shell selectors are absent;
- non-standard shell tokens are absent;
- `require("@yadsh/dsh-ui-kit")` is absent;
- `/plugins/<full-package-name>/client.js` remains the integration URL.

Required repository commands before completion:

```bash
pnpm check
pnpm deps:check
pnpm tarball:verify:packages -- packages/ui-kit <migrated-plugin-paths>
```

When a local DSH web app is available, visually compare closed, hovered,
focused, and open states against a first-party plugin card.

## 11. Compatibility and versioning

- React peer compatibility starts at `>=18.2.0 <20`, matching current plugins.
- The package targets ES2022 browser environments.
- Public component props, exported constants, CSS contract changes, and style
  lifecycle semantics are versioned API.
- Removing or renaming an export is breaking.
- Adding an optional prop is minor.
- Fixing behavior without changing the documented contract is patch.
- Because consumers embed the implementation, a UI-kit release alone does not
  update installed plugin bundles; consumers must be rebuilt and released.

## 12. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| UI kit accidentally becomes a runtime ModuleLoader dependency | Bundle assertion rejects `require("@yadsh/dsh-ui-kit")` |
| React is duplicated | All consumer configs externalize `react` and `react/jsx-runtime` |
| Style disappears when one plugin unloads | Cross-bundle reference-counted style lease |
| Shared component grows into a generic design system | Initial API is frozen to the card shell; new components require a separate spec |
| Plugin-specific styling leaks into the header | Component exposes content slots, not shell class overrides |
| CSS source and repository policy drift | Byte-equivalence test against the canonical contract |
| Published plugins depend on an unpublished workspace package | UI kit is added to Nx release and tarball workflows before consumer releases |

## 13. Required end-to-end scenarios

1. Install two migrated plugins in a clean DSH profile → both cards render with
   one shared style element and distinct bodies.
2. Unload one plugin → the remaining card keeps its shell styling.
3. Unload the final plugin → the shared style element is removed.
4. Open and close each card → body mounting, chevron rotation, and accessible
   labels remain correct.
5. Run a packed plugin without a separately loaded UI-kit client module → the
   plugin card works because UI-kit code is embedded in its bundle.
6. Remove the settings namespace from a consumer → that consumer renders no
   card, and its style lease is still released when the plugin unloads.
7. Pack and install the UI kit plus migrated plugins in a clean npm project →
   all exports resolve and no workspace protocol remains.

## 15. Acceptance criteria

The proposal is complete when:

- `@yadsh/dsh-ui-kit` is published and independently verifiable;
- all four configuration-card plugins import the shared API;
- no consumer retains a local copy of the canonical shell CSS or chevron;
- all plugin client bundles remain self-contained classic ModuleLoader scripts;
- package, dependency, test, build, bundle, and tarball checks pass;
- a first-party visual comparison shows no shell regression;
- repository documentation and the plugin generator describe the new shared
  package as the standard path for plugin configuration cards.
